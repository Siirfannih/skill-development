## Q1. "Effective context engineering": right altitude, context rot, minimal high-signal tokens

### Takeaway
Anthropic frames persistent instructions as a scarce attention budget. Prompts should sit at a "right altitude" between brittle hardcoded if-else logic and vague guidance. The aim is the minimal information that fully specifies behavior: start minimal, then add instructions only for failure modes you observe. Use a few diverse, canonical examples rather than a "laundry list of edge cases".

### Cited Findings
- Context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." — [Context engineering, Sep 29 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Attention budget: "this characteristic emerges across all models. Context, therefore, must be treated as a finite resource with diminishing marginal returns. Like humans, who have limited working memory capacity, LLMs have an 'attention budget' that they draw on when parsing large volumes of context. Every new token introduced depletes this budget by some amount, increasing the need to carefully curate the tokens available to the LLM." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Architectural reason: the transformer lets "every token to attend to every other token across the entire context. This results in n² pairwise relationships for n tokens." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Guiding principle: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Right altitude (full passage): "System prompts should be extremely clear and use simple, direct language that presents ideas at the right altitude for the agent. The right altitude is the Goldilocks zone between two common failure modes. At one extreme, we see engineers hardcoding complex, brittle logic in their prompts to elicit exact agentic behavior. This approach creates fragility and increases maintenance complexity over time. At the other extreme, engineers sometimes provide vague, high-level guidance that fails to give the LLM concrete signals for desired outputs or falsely assumes shared context. The optimal altitude strikes a balance: specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics to guide behavior." The figure caption contrasts "brittle if-else hardcoded prompts" with prompts "that are overly general or falsely assume shared context." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Minimal ≠ short, and build up from failures: "you should be striving for the minimal set of information that fully outlines your expected behavior. (Note that minimal does not necessarily mean short; you still need to give the agent sufficient information up front to ensure it adheres to the desired behavior.) It's best to start by testing a minimal prompt with the best model available to see how it performs on your task, and then add clear instructions and examples to improve performance based on failure modes found during initial testing." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structure: the post recommends organizing prompts into distinct sections with XML tags or Markdown headers, and says exact formatting likely matters less as models improve (paraphrase). — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Examples vs edge-case lists: "Providing examples, otherwise known as few-shot prompting, is a well known best practice that we continue to strongly advise. However, teams will often stuff a laundry list of edge cases into a prompt in an attempt to articulate every possible rule the LLM should follow for a particular task. We do not recommend this. Instead, we recommend working to curate a set of diverse, canonical examples that effectively portray the expected behavior of the agent. For an LLM, examples are the 'pictures' worth a thousand words." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Bloated tool sets as a failure mode: "One of the most common failure modes we see is bloated tool sets that cover too much functionality or lead to ambiguous decision points about which tool to use. If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Progressive disclosure and just-in-time context: agents "incrementally discover relevant context through exploration… maintaining only what's necessary in working memory and leveraging note-taking strategies for additional persistence." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: "Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times." It "provides persistent memory with minimal overhead. Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file…" — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction "distills the contents of a context window in a high-fidelity manner"; bigger windows won't remove the problem, since "context windows of all sizes will be subject to context pollution and information relevance concerns." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Conclusion: "the challenge isn't just crafting the perfect prompt—it's thoughtfully curating what information enters the model's limited attention budget at each step… the guiding principle remains the same: find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Same theme in the earlier post: "we recommend finding the simplest solution possible, and only increasing complexity when needed", and "you should consider adding complexity only when it demonstrably improves outcomes." — [Building effective agents, Dec 19 2024](https://www.anthropic.com/research/building-effective-agents). That page now carries a note that "Much of the tooling landscape described in this post has changed since December 2024."

### Inferences
- A one-off lesson written as a hardcoded rule ("when the file is X, do Y") is exactly the "brittle if-else" end of the altitude spectrum. Anthropic's alternative is a heuristic plus the reason for it, backed by a canonical example.
- Adding instructions is supposed to be failure-driven: test minimal first, then add only to fix observed failure modes. This argues against pre-emptively piling up rules.
- "Minimal does not necessarily mean short" heads off the opposite overcorrection. Pruning should not remove information the agent needs to behave correctly.

### Gaps
- The post gives no numeric threshold for when a prompt becomes "too long". The only numbers come from product docs (CLAUDE.md under 200 lines; SKILL.md under 500 lines; see Q2 and Q3).

## Q2. Agent Skills docs and "Skill authoring best practices": conciseness, degrees of freedom, progressive disclosure, evaluations first, Claude A/Claude B

### Takeaway
Skills should be concise ("Claude is already very smart"), and their specificity should match each task's fragility ("degrees of freedom"). They should use progressive disclosure, with SKILL.md under 500 lines and references one level deep. Skills should be built evaluation-first from observed gaps. They are refined in an observe-refine-test loop: a fresh Claude instance (B) uses the skill on real tasks, and an authoring instance (A) revises it. Anthropic's own skill-creator explicitly warns against "fiddly overfitty changes" and "oppressively constrictive MUSTs" and says to "generalize from the feedback".

### Cited Findings
**Conciseness**
- "The context window is a public good. Your Skill shares the context window with everything else Claude needs" (system prompt, conversation history, other Skills' metadata, the request). — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Default assumption: Claude is already very smart. Only add context Claude doesn't already have. Challenge each piece of information: 'Does Claude really need this explanation?' 'Can I assume Claude has this information?' 'Does this paragraph justify its token cost?'" — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "once Claude loads it, every token competes with conversation history and other context." Concise example ≈50 tokens vs verbose ≈150 tokens. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Degrees of freedom**
- "Match the level of specificity to the task's fragility and variability." High freedom (text instructions) when "Multiple approaches are valid / Decisions depend on context / Heuristics guide the approach". Medium (pseudocode or parameterized scripts) when "A preferred pattern exists / Some variation is acceptable". Low (specific scripts, few params) when "Operations are fragile and error-prone / Consistency is critical / A specific sequence must be followed." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Analogy: "Narrow bridge with cliffs on both sides: There's only one safe way forward. Provide specific guardrails and exact instructions (low freedom)… Open field with no hazards: Many paths lead to success. Give general direction and trust Claude to find the best route (high freedom). Example: code reviews where context determines the best approach." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Templates: match strictness to need. Use "ALWAYS use this exact template structure" for strict formats, and "Here is a sensible default format, but use your best judgment" for flexible ones. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Avoid offering too many options… Provide a default (with escape hatch)." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Progressive disclosure and structure**
- "Keep the SKILL.md body under 500 lines for optimal performance. Split content into separate files when approaching this limit." "Keep references one level deep from SKILL.md." Reference files over 100 lines should have a table of contents. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Progressive disclosure is the core design principle that makes Agent Skills flexible and scalable… the amount of context that can be bundled into a skill is effectively unbounded." — [Equipping agents with Agent Skills, Oct 16 2025](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- "Building a skill for an agent is like putting together an onboarding guide for a new hire." — [Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- The description carries the trigger: "Claude uses it to choose the right Skill from potentially 100+ available Skills." It should say what the skill does and when to use it, in the third person. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Time-sensitive content and pruning**
- "Avoid time-sensitive information. Don't include information that will become outdated." The bad example is "If you're doing this before August 2025, use the old API." The fix is a collapsed "Old patterns" section: "The old patterns section provides historical context without cluttering the main content." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Use consistent terminology… Consistency helps Claude parse and follow instructions." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Evaluation-driven development**
- "Create evaluations BEFORE writing extensive documentation. This ensures your Skill solves real problems rather than documenting imagined ones." Steps: "1. Identify gaps: Run Claude on representative tasks without a Skill. Document specific failures or missing context. 2. Create evaluations: Build three scenarios that test these gaps. 3. Establish baseline: Measure Claude's performance without the Skill. 4. Write minimal instructions: Create just enough content to address the gaps and pass evaluations. 5. Iterate: Run evaluations, compare against baseline, and refine." "This approach ensures you're solving actual problems rather than anticipating requirements that might never materialize." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Evaluations are your source of truth for measuring Skill effectiveness." The checklist includes "At least three evaluations created", "Tested with Haiku, Sonnet, and Opus", "Tested with real usage scenarios". — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Test across models: "What works perfectly for Opus might need more detail for Haiku… aim for instructions that work well with all of them." Opus check: "Does the Skill avoid over-explaining?" — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Engineering post, same message: "Start with evaluation: Identify specific gaps in your agents' capabilities by running them on representative tasks and observing where they struggle or require additional context. Then build skills incrementally to address these shortcomings." — [Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

**Claude A / Claude B iteration on observed behavior**
- "Work with one instance of Claude ('Claude A') to create a Skill that is used by other instances ('Claude B'). Claude A helps you design and refine instructions, whereas Claude B tests them in real tasks." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Extracting the reusable part: "Complete a task without a Skill… Notice what information you repeatedly provide." "Identify the reusable pattern: After completing the task, identify what context you provided that would be useful for similar future tasks." "Review for conciseness: Check that Claude A hasn't added unnecessary explanations." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Iterate based on observation: If Claude B struggles or misses something, return to Claude A with specifics." Use "actual tasks, not test scenarios." "Each iteration improves the Skill based on real agent behavior, not assumptions." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Note: the doc's own example of a fix suggests Claude A "might recommend… using stronger language such as 'MUST filter' instead of 'always filter'". That differs in tone from skill-creator and the Claude Code best-practices page, which discourage heavy MUSTs (see below and Q5). — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); contrasted by [skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md) and [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Observe navigation: watch for "Unexpected exploration paths… Missed connections… Overreliance on certain sections… Ignored content: If Claude never accesses a bundled file, it might be unnecessary or poorly signaled." "Iterate based on these observations rather than assumptions." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Iterate with Claude: As you work on a task with Claude, ask Claude to capture its successful approaches and common mistakes into reusable context and code within a skill. If it goes off track when using a skill to complete a task, ask it to self-reflect on what went wrong. This process will help you discover what context Claude actually needs, instead of trying to anticipate it upfront." — [Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

**skill-creator (Anthropic's own skill for writing skills): the most explicit anti-overfitting text**
- "Generalize from the feedback. The big picture thing that's happening here is that we're trying to create skills that can be used a million times (maybe literally, maybe even more who knows) across many different prompts. Here you and the user are iterating on only a few examples over and over again because it helps move faster… But if the skill you and the user are codeveloping works only for those examples, it's useless. Rather than put in fiddly overfitty changes, or oppressively constrictive MUSTs, if there's some stubborn issue, you might try branching out and using different metaphors, or recommending different patterns of working." — [skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "Keep the prompt lean. Remove things that aren't pulling their weight. Make sure to read the transcripts, not just the final outputs — if it looks like the skill is making the model waste a bunch of time doing things that are unproductive, you can try getting rid of the parts of the skill that are making it do that and seeing what happens." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "Explain the why… Today's LLMs are smart. They have good theory of mind… If you find yourself writing ALWAYS or NEVER in all caps, or using super rigid structures, that's a yellow flag — if possible, reframe and explain the reasoning so that the model understands why the thing you're asking for is important." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "Try to explain to the model why things are important in lieu of heavy-handed musty MUSTs. Use theory of mind and try to make the skill general and not super-narrow to specific examples. Start by writing a draft and then look at it with fresh eyes and improve it." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- "Look for repeated work across test cases… If all 3 test cases resulted in the subagent writing a create_docx.py… that's a strong signal the skill should bundle that script." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Baselines: "For each test case, spawn two subagents in the same turn — one with the skill, one without." When improving an existing skill, snapshot it and use the old version as baseline. An analyst pass looks for "assertions that always pass regardless of skill (non-discriminating), high-variance evals (possibly flaky)". — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Overfitting control for descriptions: the optimizer "splits the eval set into 60% train and 40% held-out test… returns JSON with best_description — selected by test score rather than train score to avoid overfitting." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Trigger eval queries should be realistic and varied ("file paths, personal context… typos or casual speech… focus on edge cases"). — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Note: skill-creator also says to make descriptions "a little bit 'pushy'" because Claude tends to "undertrigger" skills. The prompting guide warns that newer models may overtrigger on aggressive language (see Q5). The two pieces of advice pull in opposite directions; balanced trigger evals (Q4) are how to settle it. — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Inferences
- Anthropic's recommended answer to "a stubborn failure in one case" is not a narrow patch. Generalize, explain why, try a different metaphor or work pattern, and re-test on varied cases, with a held-out split where possible.
- Degrees of freedom gives a principled test for when a hard rule is right: only where the task is a "narrow bridge" (fragile, must-be-consistent, fixed sequence). Everywhere else, give heuristics.
- Reading transcripts, not just outputs, is how you find instructions that cost time without helping, which is the pruning signal.

### Gaps
- The best-practices page has no visible publication or last-updated date.
- The docs say "There is not currently a built-in way to run these evaluations" for the JSON eval format. Claude Code now has `claude plugin eval` (mentioned in tool descriptions in this environment), but I did not verify its docs here.

## Q3. Claude Code memory / CLAUDE.md docs and best practices: specificity, conciseness, review/pruning, what goes where

### Takeaway
CLAUDE.md is context, not enforced config. It should hold only what Claude can't learn from the repo, in instructions concrete enough to verify ("Use 2-space indentation"), and stay under 200 lines. Review it periodically to remove outdated or conflicting entries. Multi-step procedures belong in skills, area-specific rules in path-scoped rules, and zero-exception rules in hooks or deny rules. Current docs explicitly retire the old "IMPORTANT/YOU MUST" advice: emphasis "mostly makes Claude over-apply the rule."

### Cited Findings
**When to add (failure-driven)**
- "Treat CLAUDE.md as the place you write down what you'd otherwise re-explain. Add to it when: Claude makes the same mistake a second time; A code review catches something Claude should have known about this codebase; You type the same correction or clarification into chat that you typed last session; A new teammate would need the same context to be productive." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [Memory docs](https://code.claude.com/docs/en/memory)
- "Only write down what Claude can't find by reading the repo, or what it would otherwise spend time rediscovering every session." Test: "1. Could it find this by reading the code? 2. Would it actually go and look? If both are yes, leave it out." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- What earns a place: exact test, typecheck, and lint commands; "Places where the code is misleading"; "Decisions that aren't in the repo"; "Anything you've had to correct twice already". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Why keep it short: "every line in it takes a little of Claude's attention on every task, whether it's relevant or not." — [Best practices](https://code.claude.com/docs/en/best-practices)

**Specific and verifiable**
- "Write instructions that are concrete enough to verify: 'Use 2-space indentation' instead of 'Format code properly'; 'Run `npm test` before committing' instead of 'Test your changes'; 'API handlers live in `src/api/handlers/`' instead of 'Keep files organized'." — [Memory docs](https://code.claude.com/docs/en/memory)
- "The more specific and concise your instructions, the more consistently Claude follows them." — [Memory docs](https://code.claude.com/docs/en/memory)

**Size, structure, consistency, pruning**
- "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports "help you organize a long file but don't reduce its context cost". — [Memory docs](https://code.claude.com/docs/en/memory)
- "Structure: group related instructions under markdown headers and bullets. Organized sections are easier for Claude to follow than dense paragraphs." — [Memory docs](https://code.claude.com/docs/en/memory)
- "Consistency: if two instructions contradict each other, Claude may pick one arbitrarily. Review your CLAUDE.md files, nested CLAUDE.md files in subdirectories, and .claude/rules/ periodically to remove outdated or conflicting instructions." — [Memory docs](https://code.claude.com/docs/en/memory)
- Built-in audit: `/doctor prompt-audit` looks for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other"; it proposes edits and changes nothing until approved (requires v2.1.283+). `/doctor` "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions that differ from tool defaults." — [Memory docs](https://code.claude.com/docs/en/memory)
- `/init` output: "From there the work is mostly removing lines." — [Best practices](https://code.claude.com/docs/en/best-practices)

**Where things go**
- Scopes: managed policy (org), user `~/.claude/CLAUDE.md` ("Personal preferences for all projects"), project `./CLAUDE.md` ("Team-shared… focus on project-level standards rather than personal preferences"), local `./CLAUDE.local.md` ("Personal project-specific preferences; add to .gitignore"). — [Memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md vs auto memory: CLAUDE.md is written by you, holds "Instructions and rules", and is used for "Coding standards, workflows, project architecture". Auto memory is written by Claude, holds "Learnings and patterns", and is used for "Your preferences, corrections you give Claude, project context Claude can't derive from the code". — [Memory docs](https://code.claude.com/docs/en/memory)
- Auto memory types: `user`, `feedback` ("corrections you give Claude and approaches you confirm"), `project`, `reference`. "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." "It decides what's worth remembering based on whether the information would be useful in a future conversation." — [Memory docs](https://code.claude.com/docs/en/memory)
- MEMORY.md limit: only "the first 200 lines or 25KB" load. Near the limit, Claude Code tells Claude to "keep one line per entry, move detail into topic files, and merge or drop stale entries." — [Memory docs](https://code.claude.com/docs/en/memory)
- Skills for procedures: "how your team does a release, what your incident runbook says… That kind of knowledge goes in a skill." Skills are "lighter on context than CLAUDE.md" because only the name and description load until needed. "The CLAUDE.md rule applies to skills too: only write down what Claude can't find on its own." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Path-scoped rules: "If a rule only matters in one part of the codebase, put it in .claude/rules/ with a paths: filter so it only loads when Claude is actually working there." — [Best practices](https://code.claude.com/docs/en/best-practices)

**Guidelines vs enforcement, and why most rules should stay soft**
- "Most of the time, you want Claude to decide. Almost every guideline has exceptions, and current models are good at reading the code in front of them and judging whether a guideline fits the situation. With the actual code in front of it, Claude is usually better placed to make that call than a rule you wrote in advance." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If something has to happen every time, make it a hook, a deny rule, or a managed setting. CLAUDE.md is for guidelines, and Claude is allowed to decide a guideline doesn't apply." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook. The reverse holds too: if you have hooks for things that are only preferences, delete them and let Claude decide." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If Claude keeps ignoring a line that is in CLAUDE.md, adding IMPORTANT probably won't fix it. Either the file has grown long enough that the line gets lost, or the line is a rule that can't have exceptions." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't… If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own." "a hook is for a rule with zero exceptions, and `Prefer named exports` has plenty, so that one stays in CLAUDE.md." — [Best practices](https://code.claude.com/docs/en/best-practices)

**Retired advice (stale instructions)**
- "What you can stop doing… Most were workarounds for something the model couldn't reliably do yet." Retired items include "Add IMPORTANT or ALL CAPS to instructions Claude keeps missing", because "Older models sometimes needed the emphasis. Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule… If the line is getting lost in a long file, the file needs to be shorter." Also retired: "Tell Claude to keep going, loop until done, don't be lazy" ("more likely to cause over-work") and "Describe your architecture and file layout in CLAUDE.md" ("Claude reads the repo itself"). — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If any other advice on this page ever starts to feel like busywork, that's probably a sign it belongs in this table too." — [Best practices](https://code.claude.com/docs/en/best-practices)
- In-session: "If you've corrected the same thing twice and it's still wrong, a third correction mostly adds to a conversation that already contains two failed attempts… /clear plus one new prompt that folds in what you learned works better almost every time." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Debugging non-adherence: "Make instructions more specific… Look for conflicting instructions across CLAUDE.md files." CLAUDE.md is "delivered as a user message after the system prompt… there's no guarantee of strict compliance, especially for vague or conflicting instructions." — [Memory docs](https://code.claude.com/docs/en/memory)

### Inferences
- The trigger for writing something down is repetition: the same mistake twice, the same correction twice. One incident alone does not qualify. This is a built-in guard against encoding one-off cases.
- The docs treat over-application as a real cost. Emphasis and absolute rules make Claude apply a rule where it doesn't fit, which is overfitting in instruction form.
- The "What you can stop doing" table shows Anthropic actively pruning its own advice as models change. Instruction files are meant to be revisited, not only appended to.

### Gaps
- The original April 2025 engineering post (anthropic.com/engineering/claude-code-best-practices) now redirects, so I could not quote its earlier text live. As I recall it, it said to "tune" CLAUDE.md, warned that a common mistake is adding extensive content without iterating on its effectiveness, and suggested emphasis like "IMPORTANT"/"YOU MUST" to improve adherence. That recollection is unverified, and the current docs reverse the emphasis advice.

## Q4. Memory tool, building effective agents, writing tools, Agent Skills post, evals: turning failures into reusable guidance and checking that changes help

### Takeaway
Across these posts the loop is the same: source tasks from real failures, define unambiguous success criteria, measure against a baseline, read transcripts, and grade outcomes rather than exact paths. Test both directions (should and shouldn't) so a fix for one failure doesn't create the opposite failure. Avoid overfitting evals to particular strategies. Memory should be kept organized, current, and topic-relevant, with stale files deleted.

### Cited Findings
**Memory tool**
- Purpose: "Apply lessons from past interactions, decisions, and feedback to new tasks"; "Memory supports just-in-time context retrieval… This keeps the active context focused on the current task." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Auto-injected system prompt: "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE… As you make progress, record status / progress / thoughts etc in your memory. ASSUME INTERRUPTION: Your context window might be reset at any moment…" — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Hygiene: "when editing your memory folder, always try to keep its content up-to-date, coherent and organized. You can rename or delete files that are no longer relevant. Do not create new files unless necessary." Scope it: "Only write down information relevant to <topic> in your memory system." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- "Memory expiration: Periodically delete memory files that haven't been accessed in a long time." Cap file sizes. "Claude usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Multisession pattern: "set up memory files deliberately instead of writing them ad hoc." Key principle: "Mark a feature complete only after end-to-end verification confirms it works, not when the code is written. This keeps the progress log accurate." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

**Demystifying evals (Jan 9, 2026)**
- Why: without evals teams get "stuck in reactive loops—catching issues only in production, where fixing one failure creates others." "Absent evals, debugging is reactive: wait for complaints, reproduce manually, fix the bug, and hope nothing else regressed." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- "20-50 simple tasks drawn from real failures is a great start." "Converting user-reported failures into test cases ensures your suite reflects actual usage." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Unambiguous tasks: "A good task is one where two domain experts would independently reach the same pass/fail verdict… Ambiguity in task specifications becomes noise in metrics." Create "a reference solution". "0% pass@100 is most often a signal of a broken task." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Balanced sets, the key anti-overcorrection point: "Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization. For instance, if you only test whether the agent searches when it should, you might end up with an agent that searches for almost everything." The Claude.ai web-search work balanced "undertriggering… or overtriggering" and "took many rounds of refinements to both the prompts and the eval." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Don't over-specify paths: "There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. We've found this approach too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn't anticipate… it's often better to grade what the agent produced, not the path it took." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Capability vs regression: regression evals "should have a nearly 100% pass rate… As teams hill-climb on capability evals, it's important to also run regression evals to make sure changes don't cause issues elsewhere." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- "Step 6: Check the transcripts. You won't know if your graders are working well unless you read the transcripts and grades from many trials… the transcript tells you whether the agent made a genuine mistake or whether your graders rejected a valid solution." — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Consistency metric: "pass^k measures the probability that all k trials succeed… (0.75)³ ≈ 42%." Useful where reliable behavior every time matters. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Maintenance: "An eval suite is a living artifact that needs ongoing attention and clear ownership." Closing summary: "Source realistic tasks from the failures you see. Define unambiguous, robust success criteria… Read the transcripts!" — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Rigid grading example: Opus 4.5 scored 42% on CORE-Bench until fixes, including to "rigid grading that penalized '96.12' when expecting '96.124991…'", raised it to 95%. — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Writing effective tools for agents (Sep 11, 2025)**
- Eval tasks "grounded in real world uses"; avoid "overly simplistic or superficial 'sandbox' environments". — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "Avoid overly strict verifiers that reject correct responses due to spurious differences like formatting, punctuation, or valid alternative phrasings." "because there might be multiple valid paths to solving tasks correctly, try to avoid overspecifying or overfitting to strategies." — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Held-out test sets: the post's charts report "Held-out test set performance" of internal Slack/Asana tools after Claude-driven optimization. — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "what agents omit in their feedback and responses can often be more important than what they include. LLMs don't always say what they mean." "Review the raw transcripts… Read between the lines." — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- A generalizing fix from observed failure: Claude "was needlessly appending 2025 to the tool's query parameter… (we steered Claude in the right direction by improving the tool description)." — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

**Building effective agents (Dec 2024)**
- "The key to success, as with any LLM features, is measuring performance and iterating on implementations. To repeat: you should consider adding complexity only when it demonstrably improves outcomes." — [Building effective agents](https://www.anthropic.com/research/building-effective-agents)

### Inferences
- "Demonstrably improves outcomes" and "compare against baseline" together set a standard: a new rule or lesson should be shown to help on more than the case that prompted it, with no regressions elsewhere.
- Balanced (should/shouldn't) evals are the direct guard against overcorrection, where a lesson from one failure makes the agent apply the fix everywhere.
- "Grade the outcome, not the path" applies to instructions as well as evals. Prescribing an exact sequence of steps is brittle unless the task is a true "narrow bridge".

### Gaps
- None of these sources gives a quantitative rule for how many distinct cases must show a pattern before it gets written down. The closest are the "second time" and "corrected twice" triggers in the Claude Code docs, and skill-creator's "3 test cases" signal for bundling repeated scripts.

## Q5. Prompt-engineering guidance: "tell Claude why" and examples causing over-imitation

### Takeaway
Anthropic says to give the reason behind an instruction because "Claude can generalize from the explanation". Examples are powerful steering tools that Claude will pattern-match on, so they must be relevant and diverse enough that Claude "doesn't pick up unintended patterns". Aggressive phrasing ("CRITICAL: You MUST") now tends to cause over-triggering. The guidance also says to write general solutions rather than hardcoding to test cases.

### Cited Findings
- "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can give Claude more information about your goals and help it deliver more targeted responses." Less effective: "NEVER use ellipses". More effective: "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them." "Claude can generalize from the explanation." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Examples: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure." Make them "Relevant: Mirror your actual use case closely. Diverse: Cover edge cases and vary enough that Claude doesn't pick up unintended patterns. Structured: Wrap examples in <example> tags." "Include 3–5 examples for best results. You can also ask Claude to evaluate your examples for relevance and diversity." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Skills doc: "Examples convey the desired style and level of detail to Claude more clearly than descriptions alone." Checklist: "Examples are concrete, not abstract." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Clarity test: "Think of Claude as a brilliant but new employee who lacks context on your norms and workflows… Key test: Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Positive framing: "Tell Claude what to do instead of what not to do. Instead of: 'Do not use markdown in your response'. Try: 'Your response should be composed of smoothly flowing prose paragraphs.'" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Over-triggering from strong language: newer models are "more responsive to the system prompt than previous models. If your prompts were designed to reduce undertriggering on tools or skills, these models might now overtrigger. The fix is to soften any aggressive language. Where you might have said 'CRITICAL: You MUST use this tool when...,' you can use more normal prompting such as 'Use this tool when...' instead." Also: "Instructions such as 'If in doubt, use [tool]' cause overtriggering." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Migration: "If your prompts previously encouraged the model to be more thorough or use tools more aggressively, reduce that guidance." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Generalizing over hardcoding (sample prompt): "Implement a solution that works correctly for all valid inputs, not just the test cases. Do not hard-code values or create solutions that only work for specific test inputs. Instead, implement the actual logic that solves the problem generally… Tests are there to verify correctness, not to define the solution." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Matching evidence from skill-creator: "Explain the why… If you find yourself writing ALWAYS or NEVER in all caps… that's a yellow flag." — [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md). From Claude Code docs: emphasis "mostly makes Claude over-apply the rule." — [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- A lesson written with its reason ("X, because Y") can be applied by Claude to cases that are new but analogous. A bare rule can only be matched literally, and absolute wording can make it over-apply. So "tell Claude why" is Anthropic's main generalization mechanism for persistent instructions.
- A single example drawn from one incident risks being copied literally. Anthropic's remedy is several diverse examples, which for lessons means several contrasting cases, not one anecdote.

### Gaps
- Earlier Claude 4-era guidance had a section along the lines of "Be vigilant with examples & details" (Claude pays close attention to examples, so make sure they match the desired behavior). I recall it but did not find that phrasing on the current page, which now carries the point only as the "Diverse… unintended patterns" bullet. Treat the older wording as unverified.
- I found no Anthropic source that quantifies over-imitation, such as measured rates of copying example surface features.
